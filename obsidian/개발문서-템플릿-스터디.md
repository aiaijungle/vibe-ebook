# 개발 참고자료 — 요구사항정의서 · WBS 템플릿 스터디

> 목적: vibe-ebook 및 이후 프로젝트에서 새 기능/챕터/페이지를 만들 때 "뭘 만들지 모호한 상태로 시작하는 것"을 막기 위한 문서 템플릿 정리. Claude Code 세션에 작업을 요청할 때도 이 구조를 그대로 쓰면 왔다갔다하는 질문이 줄어든다.

## 0. 배경
- 사용자가 공유한 구글 시트(WBS/기획 관련 추정)는 Drive 연동 만료로 아직 원문을 확보하지 못함 → 재인증 후 이 노트에 이어서 반영 필요.
- `justinnoh/wbs-mockup` 목업 페이지는 별도 세션(다른 GitHub owner)에서만 접근 가능 → 그 세션에서 스터디한 내용을 이 노트에 추가 예정.
- 아래 내용은 우선 표준 SRS/WBS 구조와 국내 실무 요구사항정의서 관례를 웹 리서치로 정리한 버전.

## 1. 요구사항정의서(SRS) 표준 구조 (무거운 버전 — 외부 제출/계약용)
1. **서론**: 목적, 범위, 정의·약어, 참조 문서
2. **전체 설명**: 제품 관점, 기능 요약, 사용자 특성, 제약조건, 가정·의존성
3. **기능 요구사항**: ID 기반 추적(FR-01, FR-02…), 표 또는 Use Case 형식
4. **비기능 요구사항**: 성능, 보안, 가용성, 확장성, 유지보수성
5. **외부 인터페이스 요구사항**: UI/UX, 하드웨어, 소프트웨어(API/DB), 통신(프로토콜/포트)
6. **시스템 아키텍처 개요** (선택): 블록 다이어그램, 데이터 플로우
7. **요구사항 추적성 매트릭스(RTM)**: 요구사항 ↔ 테스트 케이스 매핑
8. **부록**: 용어집, 추가 제약사항, 참고자료

## 2. 실무용 경량 요구사항정의서 (1인 개발/소규모 프로젝트용)
계약서 수준으로 무겁게 쓸 필요 없을 때는 아래 표 하나로 충분한 경우가 많다.

| 구분 | 요구사항ID | 요구사항명 | 세부기능ID | 세부기능명 | 상세설명 | 우선순위 | 비고 |
|---|---|---|---|---|---|---|---|
| 웹/앱/사용자/관리자/공통 등 | REQ-001 | | FR-001-1 | | "무엇을, 왜, 어떤 조건에서" 명확히 | 상/중/하 | |

- 나쁜 예: "사용자는 로그인을 할 수 있어야 한다"
- 좋은 예: "사용자는 이메일과 비밀번호로 로그인할 수 있어야 한다"
→ 모호한 동사(관리한다/처리한다) 대신 구체적 행위·조건을 적는 게 핵심.

## 3. WBS(작업분해구조) 목업 표준 필드
프로젝트를 "더 이상 쪼갤 수 없는 작업 단위"까지 계층적으로 분해하는 표. 표준 컬럼:

| 필드 | 설명 |
|---|---|
| WBS ID | 계층형 번호 (1, 1.1, 1.1.1 …) |
| 작업명(Task) | 산출물 기준 명사형으로 (동사형 금지 — "설계한다"X, "설계 문서"O) |
| 상위작업(Parent) | 이 작업이 속한 상위 WBS ID |
| 담당자(Owner) | |
| 시작일 / 종료일 | |
| 소요기간(Duration) | |
| 상태 | Not Started / In Progress / Done / Blocked |
| 산출물(Deliverable) | 이 작업이 끝나면 나오는 결과물 |
| 진행률(%) | |
| 의존관계(Dependency) | 선행 작업 WBS ID |

원칙: 100% Rule(하위 작업 합이 상위 작업 범위의 100%를 커버), 8/80 Rule(개별 작업은 8~80시간 사이로 쪼갠다).

## 4. vibe-ebook 프로젝트에 적용하는 법
- 새 챕터/새 랜딩페이지 착수 전, 섹션 2 표로 "미니 요구사항정의서" 먼저 작성 → 훅/사례/데이터/CTA 등 필수 요소를 요구사항ID로 명시
- 규모가 큰 작업(예: 신간 출시, 전권 리뉴얼)은 섹션 3 WBS로 쪼개서 진행 상황을 이 노트나 별도 트래커에서 추적
- Claude Code에게 작업을 맡길 때 "요구사항ID + 상세설명" 형식으로 지시하면 왕복 질문이 줄어듦 (이번 대화에서 "미친 AI" 챕터 기획 시 여러 번 되물어야 했던 것과 대조)
