# 내 업무 하나를 검토 가능한 결과물로 끝내는 워크북

이 워크북의 목표는 “AI를 써봤다”가 아니라 다른 담당자가 근거와 결과를 대조하고, 다음 행동을 결정할 수 있는 업무 묶음을 만드는 것입니다. 읽는 순서는 **1권 → 2권 → 4권 → 3권 → 5권**입니다. 한 번에 업무 하나만 고릅니다.

완성 상태는 `ready_for_review`입니다. 이 문서에서는 **업무 묶음의 검토 준비**를 뜻합니다. 2권 프로그램이 특정 예약 요청에 반환하는 같은 문자열과는 평가 대상이 다릅니다. 문서가 완성되어도 예약·발송·결제·운영 배포를 실행했다는 뜻은 아닙니다. 실제 연동은 별도 구현·권한·검증·승인이 필요합니다.

준비물은 편집 가능한 문서, 공개하거나 사용이 허용된 업무 자료, 타이머나 시간 기록입니다. AI 계정 없이도 표와 답안을 직접 작성할 수 있습니다. 제공 Python 실습은 가상 판정 확인용이며 실제 고객 시스템에 연결되지 않습니다. [완성 예시](completed-example.md)를 먼저 훑고, 자기 업무에는 아래 빈 양식을 복사하세요. [인수 기준](acceptance-rubric.md)은 시작 전에 검토자와 함께 정합니다.

## 오늘 15분으로 시작하기

15분은 첫 작업 시간을 정하는 제안이며 완료나 효과를 보장하지 않습니다. 지금은 **업무 하나 / 담당자 / 사용할 원본 / 결과물 하나 / 다음 확인 질문** 다섯 줄만 적고 초안으로 저장하세요. 원본이 미확인이면 그 사실을 적은 초안도 남길 수 있습니다. 다만 사실 안내에 사용하기 전에는 확인이 필요합니다.

1권을 읽는 중이라면 1단계의 업무 지시서와 문안만 작성해 내보내면 됩니다. 코드 명령·승인자·운영 수치를 만들어 채우지 마세요. 나머지 단계는 해당 권을 배우고 업무에 필요해질 때 이어갑니다. 작성 도구는 미완성 상태도 저장·내보낼 수 있습니다. **작은 첫 실습의 완료와 다섯 권 전체 인수 묶음의 검토 준비는 다른 기준**입니다. 전체 과제는 선택 심화 경로이며, 모든 칸을 한 번에 채우는 것이 목표가 아닙니다.

## 0. 업무를 작게 고르기 — 첫 장에서 멈추는 기준

가능한 시작: 승인된 행사 안내에서 블로그·FAQ 초안 만들기, 접수된 요청의 누락 항목 정리, 가상 예약 자료의 사전 검토, 내부 주간 보고서 초안 작성. 처음부터 실제 예약 확정·결제·전체 고객 자동 발송까지 묶지 마세요. 그런 업무를 골랐다면 이번 범위를 “실행 전 담당자 검토 묶음”으로 줄입니다.

다음 세 질문에 답할 수 없으면 도구 선택보다 업무 확인이 먼저입니다.

| 질문 | 적을 증거 | 멈추고 할 일 |
|---|---|---|
| 무엇을 입력받아 무엇을 남기나? | 실제 입력 형식 하나와 결과물 예시 하나 | 담당자에게 완료 사례 한 건 요청 |
| 어느 자료가 맞는가? | 원본 ID·버전·책임자·확인 시각 | 정본 책임자 지정, 충돌하는 사실은 보류 |
| 누가 사용 가능 여부를 판단하나? | 검토자와 판정 항목 | 본인이 검토한다면 역할을 나누어 재검토 시각 지정 |

아래 양식의 빈칸은 추측해서 메우지 않습니다. 모르겠으면 `미확인 / 확인할 사람 / 확인 기한`을 적습니다. 예시는 가상 자료이며, 내 업무에는 실제 자료의 사용 범위와 유효 시점을 다시 확인합니다. 외부 AI에 넣을 때는 작업에 필요한 정보만 제공하고 고객 이름·연락처·비밀 값은 제거하거나 승인된 내부 환경을 사용하세요.

```text
project_id:
task_name: [동사 + 결과물 하나]
owner: [작업 담당]
reviewer: [내용·증거 검토]
approver: [실제 사용 승인, 이번 범위 밖이면 미지정이라고 적기]
scope_in: [이번에 만드는 것]
scope_out: [이번에 실행하지 않는 것]
output_artifact: [파일명과 제출 위치]
완료 단위: [검수된 안내문 1묶음 등, 호출 수와 구분]
작업 시작일 / 검토 예정일:
```

## 1. 근거와 문안 — 1권 산출물

### 1-1. 원본을 한 번 잠근 뒤 사실부터 표시하기

자료를 복사한 시점과 적용 시점은 다릅니다. 최근에 내려받았어도 오래된 정책일 수 있습니다. 원본에 있는 사실, 해석, 모르는 것을 구분합니다. 실제 원본이 바뀌면 이전 버전을 덮어쓰지 않고 변경 기록을 남깁니다.

| source_id | version | owner | checked_at | valid_until 또는 재확인 조건 | 적용 대상·기간 | 승인 근거·위치 |
|---|---|---|---|---|---|---|
| | | | | | | |

`valid_until`을 정할 근거가 없으면 임의의 날짜를 만들지 말고 “담당자 확인 전 사용 보류”로 적습니다. 일회성 공지와 잔여 좌석처럼 수시로 바뀌는 정보의 유효 조건을 같게 두지 않습니다.

| 확인할 사실 | 원문 값 | 근거 위치 | 문안에 쓸 값 | 미확인 질문 |
|---|---|---|---|---|
| 날짜·시간 | | | | |
| 금액·단위·조건 | | | | |
| 대상·장소 | | | | |
| 다음 행동 | | | | |

### 1-2. 초안과 변경 전후를 함께 제출하기

```text
입력: 위 source_id/version의 승인된 사실만 사용한다.
업무: [독자가 다음에 해야 할 행동]을 알 수 있는 [결과물]을 만든다.
출력 형식: [제목 / 본문 / FAQ 등].
모르는 정보는 만들어 넣지 않고 확인 질문으로 분리한다.
완료 조건: 날짜·금액·대상·다음 행동이 원문과 일치한다.
함께 남길 것: 사용 근거 ID, 확인할 질문, 검토가 필요한 표현.
```

| 결과물·문장 ID | 변경 전 | 변경 후 | 바꾼 근거·이유 | 검토 결과 |
|---|---|---|---|---|
| | | | | 유지 / 수정 / 보류 |

**인수 증거:** 원본, 초안, 수정본, 사실 대조표를 함께 보관합니다. 예쁘게 다듬은 최종본만 남기면 무엇을 고쳤는지 검증할 수 없습니다. 두 채널을 만든다면 말투 대신 날짜·금액·대상·다음 행동이 같은지 대조합니다. 허위 링크·혜택·성과 약속이 하나라도 남으면 발행 후보에서 제외합니다.

## 2. 요구사항과 상태표 — 2권 산출물

### 2-1. 화면보다 상태를 먼저 정하기

내 업무의 최소 입력과 누락 시 행동을 적습니다. 숫자 0은 값이 없는 상태가 아닙니다. 숫자·날짜·단위를 확인하고 서로 다른 기준 시각의 자료를 섞지 않습니다.

| input_field | 형식·단위 | 필수 여부 | 누락 시 처리 | 근거 |
|---|---|---|---|---|
| | | | | |

2권 공통 실습은 `needs_information`(확인 필요), `blocked`(확인된 조건 불충족), `ready_for_review`(검토 준비)를 사용합니다. 모두 `executed=false`입니다. 내 프로그램에서 다른 상태명을 쓴다면 대응표를 만들고 고객 안내 문구와 내부 상태를 분리하세요.

| case_id | 입력·기준 시각 | expected_status | 보여줄 말·다음 행동 | actual_status | evidence | result |
|---|---|---|---|---|---|---|
| T01 정상 | | | | 미실행 | | |
| T02 필수 정보 누락 | | | | 미실행 | | |
| T03 확인된 조건 불충족 | | | | 미실행 | | |
| T04 충돌·중복 | | | | 미실행 | | |
| T05 오래된 자료 | | | | 미실행 | | |

처음에는 종이 판정으로 표를 작성해도 됩니다. **수동 대조 / 제공 가상 코드 실행 / 내 앱 통합 실행** 중 어떤 방식의 증거인지 표시하세요. 종이에서 맞은 답을 앱 테스트 통과라고 적지 않습니다. 승인받지 않은 실제 고객 입력으로 오류를 재현하지 않습니다.

### 2-2. 실패를 다음 행동으로 바꾸는 분기표

```text
근거가 없거나 서로 충돌한다
  → needs_information으로 보류 → 정본 책임자에게 질문 → 확인 후 같은 사례 재검토
조건이 확인되었고 충족하지 못한다
  → blocked → 충족 조건이나 다른 선택지를 안내 → 임의 승인하지 않음
조건은 맞지만 승인이 없다
  → 사전 검토 결과를 승인자에게 전달 → 실제 실행하지 않음
실행 요청 뒤 결과를 확인하지 못했다
  → 실패로 단정하지 않음 → 기존 요청 ID로 조회 → 확인 전 새 실행 금지
프로그램이 예상과 다르게 판정한다
  → 입력·기대·실제·버전 보존 → 4권 수정 증거 단계로 이동
```

**인수 증거:** 다섯 행의 예상과 실제, 판정 이유, 다음 행동. 구현하지 않았다면 실제 결과 칸을 수동 대조로 표시하고 앱 검사는 미실행으로 남깁니다. 최종 문서의 검토 준비와 앱 가동 준비를 섞지 않습니다.

## 3. 작은 변경과 재현 증거 — 4권 산출물

정상 동작을 일부러 망가뜨릴 필요는 없습니다. 오류가 없다면 현재 상태를 확인하고 변경 없음으로 남깁니다. 실패 연습이 필요하면 가상 사본에서만 수행합니다.

```text
change_id:
reason: [어떤 입력에서 어떤 기대와 다른가]
현재 버전 / 복구할 버전:
재현 입력과 기준 시각:
기대 결과 / 실제 결과:
수정 범위 / 유지할 업무 규칙:
files: [수정한 파일과 이유, 변경 없으면 없음]
verification_mode: [manual 또는 command]
manual_evidence: [수동 대조표·원문·변경 전후 증거 위치]
not_applicable_reason: [명령 검사가 해당 없는 이유, 예: 문안 교정만 수행]
commands: [실행 위치와 명령 그대로; 수동 검토이면 빈 목록]
exit_codes: [실제 값; 수동 검토이면 빈 목록, 가짜 0을 넣지 않음]
증거 위치: [출력·diff·검사 기록]
unrun: [실행하지 않은 검사와 이유]
rollback_version: [되돌릴 코드/문서 버전]
```

수정 전 같은 실패를 확인하고, 수정 후 그 사례와 정상 사례를 다시 확인합니다. 통과하도록 정답을 바꿨다면 변경 이유와 정책 승인 근거가 필요합니다. 출력 CSV를 손으로 맞추는 것은 비교기 실험일 수는 있지만 제품 결함 수정의 증거가 아닙니다.

3·4권 제공 검사기는 가상 원장의 `needs_evidence`, `awaiting_approval` 등을 검사합니다. 2권의 잔여 횟수 판정을 대신 검사하지 않습니다. 사용할 검사와 파일이 같은 과제를 가리키는지 확인하세요. 종료코드 0은 그 명령이 성공했다는 증거이지 고객 흐름 전체 성공의 증거가 아닙니다. PostToolUse처럼 실행 후 확인하는 장치는 이미 발생한 변경을 자동으로 취소하지 않습니다.

**인수 증거:** 변경 전 재현, 최소 변경 diff, 변경 후 검사, 미실행 목록. 코드가 없는 문안 작업은 원문 대조와 변경 전후 표를 사용하고 명령·종료코드는 해당 없음으로 표시합니다.

## 4. 실행 계획과 사람 승인 — 3권 산출물

초안 생성, 검토, 승인, 실제 실행은 다른 단계입니다. 같은 사람이 여러 역할을 맡아도 각 결정의 시각과 근거를 나눠 남깁니다. 이 워크북은 실행 계획과 승인 요청서까지 작성하며 실제 실행 도구는 연결하지 않습니다.

| 역할 | 받는 것 | 남기는 것 | 할 수 없는 일 |
|---|---|---|---|
| 작성자 | 승인된 원본 | 문안·검토 제안 | 자기 결과를 실행 완료로 선언 |
| 검토자 | 원본·출력·검사 증거 | 승인 요청 또는 수정 요청 | 누락 근거를 추측해 승인 |
| 승인자 | 버전이 고정된 제안 | 대상·인자를 포함한 결정 | 변경된 제안에 옛 승인 재사용 |
| 실행 담당 | 유효한 승인·권한 | 실제 결과 ID·확인 기록 | 결과 미확정 상태에서 무조건 재시도 |

```text
proposal_id:
version: [내용과 실행 도구 버전]
target: [누구에게 / 어느 자원에]
args: [금액·시간·내용·대상 등 검토한 값]
expires_at: [승인 유효 조건, 미정이면 실행 불가]
검토 증거 / 미해결 질문:
승인자 / 승인 시각:
decision: [pending — 검토 대기 / not_requested — 아직 요청 안 함 / approved — 실제 지정 범위 승인 / rejected — 거절]
주의: expires_at은 제안의 유효 조건이며 승인 증거가 아니다. 검토 준비에는 approved가 필수가 아니다.
이번 워크북의 외부 실행: 없음
```

가상 원장 실습의 상태는 `recorded`, `needs_evidence`, `awaiting_approval`, `already_recorded`, `reconcile_required`입니다. `recorded`는 로컬 목록에 기록했다는 뜻이며 실제 예약 성공이 아닙니다. 도구 결과가 불명확하면 실제 외부 상태가 0건이라고 추정하지 않습니다. 반복 실행을 설계할 때는 요청 ID와 결과 ID를 보존하고, 서비스가 중복 방지를 보장하는지 별도로 확인해야 합니다.

**인수 증거:** 역할표, 버전이 고정된 제안, 미해결 질문, 실행하지 않은 범위. 승인자 서명란을 작성자가 대신 채우지 않습니다.

## 5. 결과 한 건의 비용과 운영 인계 — 5권 산출물

### 5-1. 비교는 같은 업무와 같은 합격 기준으로

처음에는 익숙한 수동 방식과 AI를 보조로 쓴 방식을 같은 입력 묶음으로 비교합니다. 먼저 실행한 덕분에 자료를 외운 효과가 있으면 기록하세요. 적은 표본의 차이를 평균 성과나 매출 상승으로 확대하지 않습니다. 도구를 사용하지 않았다면 AI 방식의 시간을 예상값으로만 적고 실제 측정과 구분합니다.

| method | 요청 수 | unique_accepted | api_cost | tool_cost | prep_minutes | work_minutes | review_minutes | rework_minutes | hourly_value |
|---|---|---|---|---|---|---|---|---|---|
| 기존 방식 | | | | | | | | | |
| 보조 방식 | | | | | | | | | |

```text
총시간 = 준비 + 작성·실행 + 검수 + 재작업
비교용 총원가 = API 비용 + 배분한 도구비 + 총시간÷60×시간당 가치

```

동일 결과를 세 번 재시도해도 성공은 한 건입니다. 버린 결과·실패·재시도의 비용을 분자에서 빼지 않습니다. API 비용에 재시도분이 이미 포함되어 있으면 다시 더하지 않습니다. 유효 결과가 0이면 건당 원가는 산출 불가입니다. 대기 중인 건수·가장 오래 기다린 시간도 적어 검수자의 부담을 확인합니다. 현금 지출과 사람 시간의 계산 가치는 별도 열로 유지합니다.

### 5-2. 멈춘 뒤 다른 사람이 이어받을 수 있게

| 항목 | 내 업무의 기록 |
|---|---|
| stop_condition | 근거 만료 / 중요 오답 / 예산·검수 여력 초과 중 해당 조건과 수치 |
| stop_owner | 멈출 담당자와 대체 담당자 |
| 중단 범위 | 어떤 작업만 멈추며 어떤 조회는 유지할지 |
| 마지막 정상 결과 | ID·버전·시각·검수 여부 |
| pending_requests | 요청 ID·상태·이미 처리됐는지 확인 여부 |
| reconcile_before_retry | 기존 결과 조회 방법·담당자·확인 불가 시 보류 방법 |
| rollback_version | 되돌릴 문서·코드 버전, 이미 실행한 결과의 별도 처리 |
| resume_checks | 원인 해소·권한·원본 유효성·예산·중복 확인·시험 검토 |

이번 오프라인 과제에서 예산 정지나 중복 방지는 **설계 기록**입니다. 실제 호출을 차단하는 기능으로 작동하지 않습니다. 코드 복구로 이미 보낸 메시지나 확정된 예약이 취소되지 않습니다. 실제 운영 전에는 위 조건을 도구와 서버에서 구현하고 검증해야 합니다.

## 6. 2주 진행표 — 결과를 보장하지 않는 작업 일정

첫날 시작 날짜를 적고 아래 작업일을 실제 달력에 배치하세요. 1주차 5일, 2주차 5일을 기본으로 하며 주말 4일은 비워둡니다. 일정이 밀리면 미완료 단계와 새 검토일을 적고, 검사를 생략해 날짜를 맞추지 않습니다. 각 날에 쓸 수 있는 시간을 직접 정하세요.

| 작업일 | 할 일 | 남길 증거 | 다음 단계로 가는 조건 |
|---|---|---|---|
| 1 | 업무 하나·범위·검토자 정하기 | 과제 카드 | 입력·결과·판정자 확정 |
| 2 | 원본과 사실 확인 | 원본 목록·미확인 질문 | 근거 충돌 해소 또는 명시적 보류 |
| 3 | 기존 방식으로 샘플 처리 | 결과·시간 기록 | 합격 기준과 완료 단위 고정 |
| 4 | 보조 방식으로 같은 과제 처리 | 초안·원문 대조·시간 | 추측한 사실 제거 |
| 5 | 다섯 상태를 예측·확인 | 상태표·수동/코드 증거 구분 | 실패의 다음 행동 정의 |
| 6 | 문제 하나 수정 또는 변경 없음 확인 | 변경 전후·검사·미실행 | 정상 사례도 유지 |
| 7 | 역할과 승인 묶음 작성 | 제안 ID·버전·권한 경계 | 실제 실행과 검토 분리 |
| 8 | 비용·검수 대기·중단 조건 계산 | 원가표·인계표 | 누락·중복 합산 해소 |
| 9 | 다른 사람이 인수 기준으로 검토 | 보완 요청·재검토 결과 | 중요 누락 없음 |
| 10 | 관리자 한 장과 다음 실험 결정 | 아래 인수 결정서 | ready_for_review 또는 보류 이유 명시 |

검토자가 없으면 다음 날 자신이 원본부터 다시 대조하고 “자체 검토”라고 표시합니다. 독립 검토를 했다고 쓰지 않습니다. 다음 반복에서는 문제 하나만 고릅니다. 예: 초안 길이 변경, 입력 항목 추가, 누락 안내 수정. 원본과 정답을 고정한 채 비교하고, 정책이 바뀌면 평가 자료도 버전을 올립니다.

`ready_for_review`는 인수 검토를 시작할 자료가 준비됐다는 뜻입니다. 관리자는 [인수 기준](acceptance-rubric.md)에 따라 재검토하고, 실제 사용 승인은 별도로 남깁니다. 비어 있는 필수 항목·근거 없는 사실·설명되지 않은 중요 실패가 있으면 보류합니다. 분량을 늘리는 대신 그 빈칸 하나를 해결하는 것이 다음 작업입니다.
